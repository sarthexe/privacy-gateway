# Phase 1 — Tokenization engine

### Use: **Codex**

This is the first real engineering phase.

Build:

```text
Input
  ↓
PII detection
  ↓
Entities
  ↓
Token generation
  ↓
Token mapping
  ↓
Tokenized text
````

Example:

```text
My name is John Smith and email is john@example.com
```

becomes:

```text
My name is <PII_PERSON:abc123>
and email is <PII_EMAIL:def456>
```

Create interfaces before implementations:

```python
class PIIDetector(Protocol):
    async def detect(self, text: str) -> list[Entity]:
        ...


class Tokenizer(Protocol):
    async def tokenize(
        self,
        text: str,
        entities: list[Entity]
    ) -> TokenizedText:
        ...
```

### Give Codex this job

Implement Phase 1 of the privacy gateway.

Scope ONLY:

1. PII detection abstraction
2. Presidio-based detector implementation
3. Entity model
4. Token model
5. Token generation
6. Tokenized text representation
7. Reconstruction/detokenization abstraction
8. Unit tests

Supported initial entity types:

* PERSON
* EMAIL
* PHONE_NUMBER
* CREDIT_CARD
* IP_ADDRESS
* DATE_TIME
* LOCATION

Requirements:

* deterministic behavior within a request/session
* unique token IDs
* token format must be machine parseable
* no raw PII in logs
* preserve original text offsets correctly
* support multiple identical entities
* support repeated occurrences of the same entity
* never mutate the original input
* write comprehensive unit tests

Do not implement LiteLLM yet.
Do not implement PostgreSQL persistence yet.
Do not implement authentication yet.

At the end, provide:

* files changed
* architecture decisions
* edge cases handled
* tests added

# Phase 2 — Secure vault

### Use: **Claude Code**

This is where I'd spend Claude.

Because now you're crossing into:

```text
PII
+
encryption
+
persistent storage
+
tenant isolation
````

You want a second, stronger reasoning pass rather than blindly generating CRUD.

The architecture should become:

```text
Token
  ↓
Vault
  ↓
Encrypted value
```

Database roughly:

```text
token_mapping
-------------------------
id
tenant_id
token_id
entity_type
ciphertext
nonce
created_at
expires_at
```

Do **not** store:

```text
token_id → plaintext PII
```

Store:

```text
token_id → encrypted PII
```

### Claude's task

Ask Claude Code to **design/review first**, not immediately code everything.

Review the existing privacy gateway repository and design the secure vault layer.

The system is a privacy-preserving LLM gateway:

request
→ PII detection
→ tokenization
→ vault
→ LiteLLM
→ model
→ reconstruction

Design the vault with these goals:

* encrypted sensitive values at rest
* tenant isolation
* least-privilege access
* no plaintext PII in application logs
* secure token lookup
* explicit authorization before detokenization
* support token expiration
* prevent token enumeration
* avoid storing unnecessary sensitive metadata

Use PostgreSQL + SQLAlchemy.

Use authenticated encryption such as AES-GCM for the prototype.

Before modifying code:

1. inspect the repository
2. identify security risks
3. propose the vault architecture
4. explain key-management boundaries
5. explain what must never be logged
6. identify attack paths

Then implement the vault.

Add security-focused tests, including:

* cross-tenant access
* invalid token lookup
* expired token
* unauthorized detokenization
* ciphertext integrity failure
* repeated token lookup

````

### Important

For the portfolio project, don't pretend you've built an enterprise HSM/KMS system.

Call the first version:

> application-level encrypted vault

Then later you can add AWS KMS / GCP KMS / Azure Key Vault abstraction.

Vault

Tokenized messages

        ↓

LiteLLM

        ↓

        ↓

Tokenized response

        ↓

Reconstruction

        ↓

Original response
````

Codex should implement the plumbing.

### Prompt

Implement the LLM proxy pipeline.

Endpoint:

POST /v1/chat/completions

The pipeline must be:

1. authenticate request
2. extract chat messages
3. detect PII
4. tokenize sensitive entities
5. persist token mappings in the vault
6. send ONLY tokenized content to LiteLLM
7. receive model response
8. detect token references in the response
9. authorize reconstruction
10. detokenize
11. return an OpenAI-compatible response

Requirements:

* use LiteLLM for provider routing
* preserve OpenAI-compatible request/response structure
* support system/user/assistant messages
* preserve token identity across a request
* never send original PII to the LLM provider
* never log raw prompt/response content
* add integration tests proving that the outbound LLM request contains tokens rather than PII

Create a fake/mock LLM provider for tests.

Do not add UI.
Do not add billing.
Do not add unnecessary provider-specific code.
